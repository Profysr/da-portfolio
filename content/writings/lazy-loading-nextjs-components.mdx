## Why This Exists

Most "lazy loading" tutorials show you `dynamic(() => import(...))` and stop there. They don't tell you:

- How to **decide which components** actually deserve it
- What **`ssr: true` vs `ssr: false`** means for your build pipeline
- How to **prevent layout shift** when the chunk arrives
- Why your **static build fails** with "Element type is invalid"
- How to **measure** whether it actually helped

This guide covers all of it — from identification to production measurement.

## 1. The Decision Matrix: Should This Component Be Lazy?

Before you reach for `next/dynamic`, answer these four questions:

| Question | Yes → Lazy Candidate | No → Keep Static |
|----------|---------------------|------------------|
| **Bundle impact** | 50KB+ gzipped (check via `next-bundle-analyzer`) | `<20KB` or already tree-shaken |
| **Interaction trigger** | Only renders after user action (click, scroll, hover) | Visible above fold or in initial SSR |
| **Client-only APIs** | Uses `window`, `canvas`, WebGL, GSAP, `IntersectionObserver` | Pure React + CSS |
| **SEO relevance** | Zero (modal, drawer, palette, heavy chart) | Content Google should index |

**Rule of thumb:** If it's in the initial viewport *and* contains indexable content → **don't lazy load**. The SSR payload is cheaper than the hydration + chunk fetch waterfall.

### Real Examples from This Portfolio

| Component | Size | Trigger | Decision |
|-----------|------|---------|----------|
| `AIAssistant` (chat drawer) | ~45KB | Dock click | ✅ Lazy |
| `CommandPalette` | ~18KB | ⌘K | ✅ Lazy |
| `HorizontalScroll` (GSAP engine) | ~12KB | TechStack section | ✅ Lazy |
| `Timeline` (motion/react) | ~10KB | Experience section | ✅ Lazy |
| `ProjectCard` | ~8KB | Projects grid (8×) | ✅ Lazy |
| `Hero`, `About`, `TechStack` headers | `<5KB` each | Above fold | ❌ Static |
| `Button`, `Card`, `Badge` | `<1KB` | Everywhere | ❌ Static (tree-shaken) |
